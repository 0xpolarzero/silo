# Silo review remediation plan

Execution plan for every finding of the
[2026-09-29 codebase review](research/codebase-review-2026-09-29.md), including
the owner decisions recorded there. The review summary lists the most important
items; this plan's [ledger](#ledger) lists **all** findings from the 20 reviewer
reports and the consolidating reviewer, deduplicated (merged entries name every
source area).

Nothing in this plan has been implemented. It was written against `main` at
`82e3842`; the review itself was of `60b23ca`.

## How to read the ledger

Each entry has an ID (`<work package>-<number>`), a severity, flags, the
problem with its main locations, the fix, and how to verify it.

Flags:

- **✓** re-checked in code by the consolidating reviewer.
- **S** suspected: depends on runtime, OS or upstream behaviour; reproduce
  before fixing, and close as *Not reproducible* if it does not reproduce.
- **⟳** the primary file changed after `60b23ca` (see
  [changed files](#files-changed-after-the-review)); re-verify before fixing.
- **D#** implements owner decision # from the review.
- **×n** found independently by n reviewers.
- **design** needs a short design note before coding (see
  [design notes](#phase-0--prepare)).

Verification tags:

- `unit` Vitest or Cargo unit/integration test that fails before the fix.
- `ci` CI workflow or script test.
- `mac` / `linux` live check on that platform with a real local VM.
- `2pc` live check with two computers (remote management).
- `gh` live check against a disposable GitHub repository and App installation.
- `release` release pipeline dry run.

Status: every entry starts **Open**. The coordinator (and only the coordinator)
appends one of **[Fixed `<sha>`]**, **[Already fixed `<sha>`]**, **[Won't fix:
reason]**, **[Not reproducible]**, or **[Blocked: reason]** to the entry.

## Ground rules for every fix

These restate `AGENTS.md` for this effort.

1. Write the failing test first (`unit`), then the fix. Frontend tests use
   deterministic fixtures; backend tests use runner fakes and temp dirs, never
   real `$HOME`, keychain, or the user's running app or VMs.
2. One commit per ledger entry (or a tightly related group), with the IDs in the
   subject, e.g. `Fix B-02: detach every token VM before OAuth narrowing`.
3. User-visible changes get a changeset in `app/SiloUI/.changeset/`. Before 1.0
   use `patch` for fixes and `minor` for features **and breaking changes**; never
   `major` (decision 11).
4. Stay inside your work package's owned files (see
   [work packages](#work-packages)). If a fix needs another package's file,
   record the dependency on the entry and hand that part to the owner.
5. Do not print or commit credentials, `github-build.local.json`, signing
   material or private logs. Keep evidence under
   `app/SiloUI/src-tauri/target/verification/` or a temp path.
6. Report exactly what was verified: a unit test proves behaviour against its
   fixture, a build proves compilation; neither proves live VM, two-computer or
   release behaviour (those need the matching live tag).

## Orchestration

- **Agents.** One implementation agent per package; the coordinator runs the
  merge queue and owns this ledger. Up to 20 agents can run at once, but Rust
  packages should not exceed three concurrent builds.
- **Worktrees and branches.** Each package works in its own worktree on
  `fix/<wp>-<batch>` (for example `fix/b-1`), created from current `main`.
  Frontend worktrees can symlink `app/SiloUI/node_modules` from the main
  checkout; Rust worktrees set their own absolute `CARGO_TARGET_DIR`.
- **Native tests.** Use the explicit synthetic GitHub configuration the release
  guide permits for native unit tests; never distribute those executables.
- **Merge queue.** One batch at a time, performed by the coordinator:
  1. Rebase the batch branch onto `main` in its worktree; on non-trivial
     conflicts, return the batch to its agent.
  2. Run the gates: `typecheck`, `lint`, `npm test`, `test:release`, the
     `website/` and `demo/` typechecks, and when Rust changed,
     `cargo test --locked -- --test-threads=1`.
  3. `git merge --ff-only` into `main`; remove the worktree and branch.
  4. Append the terminal status and commit SHA to each ledger entry in a
     separate docs commit.
- **Batch size.** Merge small and often (at most about ten entries per batch)
  so rebases stay trivial.
- **Blocked entries.** When an entry cannot proceed (missing dependency,
  failing reproduction, needs an owner call), mark it **[Blocked: …]** and move
  on; the coordinator raises owner questions in one batch, not one at a time.
