# Linux remote desktop and session platforms

Research date: 2026-09-27. This is a documented-capability comparison for embedding Linux VM desktops in a macOS/Linux application. It is not a reliability, latency, CPU, or usability benchmark. No candidates were installed or measured for this report.

## Recommendation

For an app that owns each Linux VM and wants a native, offline-capable experience, advance two open-source RDP paths: **GNOME Remote Desktop + FreeRDP** for a modern Wayland desktop, and **xrdp/xorgxrdp + FreeRDP** when X11 and independent virtual sessions are acceptable. FreeRDP provides an Apache-2.0 native RDP client library and recent macOS/Linux client work. GNOME Remote Desktop uses PipeWire/Mutter/libei with an RDP backend; current upstream docs describe headless single-user sessions and GDM-backed headless login. xrdp provides virtual Xorg sessions and reconnectable sessions. Neither path gives a turnkey native app view. GNOME Remote Desktop is the more coherent Wayland-first experiment; xrdp has a clearer independent Xorg session model and broader established RDP channel support. Qualify lifecycle, IME, clipboard, HiDPI, and audio in a real prototype before selecting either.

Advance **Xpra** alongside it if the desired interaction is a persistent desktop/app session that can be disconnected and resumed, including over a local socket, vsock, or SSH. It documents that exact session model and has native macOS/Linux clients plus an HTML5 client. Its client/server protocol and native UI entail more product integration than an ordinary RDP SDK, but this is the strongest open-source session-focused candidate. Prefer the current 6.5 stable branch after qualification; do not carry over older reliability claims.

Keep **Amazon DCV Web Client SDK** as a paid product-quality benchmark or future hosted-workstation option, not a current default for locally managed Silo VMs. It offers a customized embedded web client and a notably rich desktop feature set, but its Linux ARM64 server support is explicitly tied to EC2 instance types, non-EC2 use needs a floating production license per concurrent session, it requires X11, and the Web SDK is limited to two monitors. Those restrictions conflict with running the same product on local ARM64 Linux VMs.

Apache Guacamole is a capable web gateway and API, but it adds a Java web application, `guacd`, and protocol plugins for a single app-owned VM. RustDesk is an end-user remote-control client and rendezvous/relay platform, not an embeddable viewer SDK or a managed Linux session server. PCoIP Client SDK is a genuine commercial embedding SDK, but its public Linux guide still documents Ubuntu 18.04/20.04 and its 2022–2023 SDK documentation is too old to establish a supported 2026 deployment. Do not choose any of those without a product requirement that matches their architecture and fresh vendor confirmation where applicable.

Also benchmark **NoMachine** if a proprietary, full client/server product is in scope: its Linux virtual-desktop server products provide persistent reconnectable desktops, but there is no public embedding SDK and its current public server support matrix needs vendor confirmation for modern Linux and generic ARM64. **ThinLinc** is a credible, commercially supported persistent X11 terminal server, but its server is x86-64-only and the vendor says Wayland support is planned; it has no public viewer SDK. These may be strong workstation products without being suitable embedded components. **Parsec** is not a Linux VM host option: its current official compatibility guide only permits Windows/macOS hosts, with Linux as a client.

## Keep the layers distinct

A desktop environment starts the user's graphical applications. Xorg/Wayland or a virtual display owns the graphical session. The server captures or renders that session and encodes it; the transport carries pixels and user input; a client renders them and bridges host keyboard, clipboard, displays, audio, and files. A protocol client does not itself create a persistent Linux session. For example, FreeRDP is a client library, xrdp is the Linux RDP server/session manager, and xorgxrdp supplies its Xorg display modules. Amazon DCV combines the Linux capture/virtual-display server with a proprietary transport and several client choices.

For an app-owned VM, connect the host to a per-VM listener through an authenticated local transport or an authenticated remote route. Avoid a generic internet-reachable desktop gateway unless the product adds multi-user brokering. Treat keyboard, clipboard, file redirection, and audio channels as explicit data boundaries and set defaults to match the trust boundary between host and guest. No upstream feature list proves that an integration preserves host trust prompts, guest identity, or reliability.

## Key evidence and caveats

### RDP stack

The [xrdp project README](https://github.com/neutrinolabs/xrdp) states that xrdp accepts standard RDP clients, uses TLS transport by default, supports reconnecting to an existing session, resizing, clipboard transfer, audio/microphone modules, and drive redirection. It requires [xorgxrdp](https://github.com/neutrinolabs/xorgxrdp) for its best Xorg mode. Its README says x86 and ARM are the most mature server architectures and notes SIMD-specific x86 acceleration, which makes ARM support credible but not a performance guarantee. The current upstream release is [xrdp 0.10.6.1](https://github.com/neutrinolabs/xrdp/releases/tag/v0.10.6.1), released July 7, 2026. The [current channel configuration](https://github.com/neutrinolabs/xrdp/blob/devel/xrdp/xrdp.ini.in) enables RDP drive, sound, dynamic virtual channel, and clipboard channels by default; configure each channel to fit the host/guest trust boundary.

### GNOME Remote Desktop and FreeRDP

The [GNOME Remote Desktop project](https://github.com/GNOME/gnome-remote-desktop) identifies its dependencies and modes: it uses PipeWire for pixel streaming, libei for input, Mutter's remote-desktop API, FreeRDP for RDP, and LibVNCServer for VNC. Upstream licenses the server GPL-2.0-or-later. Its [configuration guide](https://github.com/GNOME/gnome-remote-desktop/blob/main/docs/configuration.md) separates three operational modes:

- Remote assistance shares an already active desktop. Locking the screen closes the remote connection; this is session sharing, not a detached worker desktop.
- Headless single-user starts the server in an independently prepared headless graphical user session using the user systemd service.
- Headless multi-user remote login delegates to GDM and RDP. A shared system credential reaches the greeter, then each user authenticates with their own account.

GNOME's [NEWS file](https://github.com/GNOME/gnome-remote-desktop/blob/main/NEWS) records persistent remote-login sessions in the 47 development series, HiDPI support, virtual-monitor support, and more reliable session handover in the 49/50 series. [GNOME 50 GDM release notes](https://github.com/GNOME/gdm/blob/main/NEWS) say GDM removed its own X11 session backend. This makes GNOME RD a credible Wayland-native alternative rather than an RDP wrapper over Xorg. It also means the entire GDM/GNOME/Mutter/PipeWire stack and version alignment become deployment requirements.

The official docs require explicit TLS key/certificate configuration and credentials via `grdctl`; the project cautions against exposing remote desktop to the open Internet. Build a per-VM certificate/authentication scheme and trust prompt for the native viewer. The upstream docs do not provide one consolidated feature matrix for file transfer, audio, multi-monitor, keyboard IME, ARM, or reconnect behavior across every RDP client and GNOME version. Do not inherit FreeRDP client feature lists as proof of what the GNOME server implements. Ubuntu 24.04 carries GNOME 46-era packages, so test the exact available GRD, GDM, and Mutter packages if that distribution matters; current `main` documentation and 50-series notes are not evidence that every feature exists in its original packages.

[FreeRDP](https://github.com/FreeRDP/FreeRDP) is Apache-2.0, exposes `libfreerdp`, and builds clients for X11, Wayland, macOS, Windows, Android, and SDL. The latest release on the research date is [3.32.0, September 23, 2026](https://github.com/FreeRDP/FreeRDP/releases/tag/3.32.0), whose release notes report hardening against protocol violations/exploits and changes to certificate policy in the proxy. This confirms active maintenance, not a stable external API or proven security. Its low-level C callbacks and renderer lifecycle create an FFI and native-rendering project; assess API compatibility and native dependencies before committing to it. Do not treat `xfreerdp` command-line success as evidence that Silo's embedded client has the same UX.

### Xpra

The [Xpra project documentation](https://github.com/Xpra-org/xpra/blob/master/docs/README.md) defines persistent remote applications/desktops with disconnect/reconnect, and covers launching desktops, seamless apps, and shadowing existing displays. The [native/HTML5 client matrix](https://github.com/Xpra-org/xpra/blob/master/docs/Usage/Clients.md) lists native macOS and Linux clients and meaningful differences in audio, clipboard, keyboard, file transfer, DPI, and acceleration. Its [clipboard docs](https://github.com/Xpra-org/xpra/blob/master/docs/Features/Clipboard.md) explicitly warn that macOS uses polling and Wayland restricts clipboard synchronization. As of this date, [6.5.3 is the latest release](https://github.com/Xpra-org/xpra/releases/tag/v6.5.3), published August 18, 2026; its notes include connection-drop and clipboard fixes. These are reasons to pin and qualify exact versions, not evidence of defect rate.

Xpra's protocol security is configurable rather than implicit. Use its supported authenticated TLS/SSH/local transports, refuse cleartext passwords, restrict untrusted network exposure, and review file/URL forwarding options. The native client with local transports is a more direct in-app fit than operating an HTML5 gateway, but there is no documented cross-platform drop-in view for Tauri.

### Guacamole

The [Guacamole 1.6.0 manual](https://guacamole.apache.org/doc/gug/introduction.html) and [API docs](https://guacamole.apache.org/api-documentation/) distinguish the HTML5 client/API from the `guacd` proxy and protocol plugins. Official Docker deployment documents separate `guacd`, web application/Tomcat, and optional database containers. The client understands Guacamole's display/input protocol, not raw RDP or VNC. The [user guide](https://guacamole.apache.org/doc/gug/using-guacamole.html) says file transfer depends on the target protocol and lists VNC, RDP, and SSH. Keep `guacd` reachable only by the trusted web tier or the local app; its protocol backends carry credentials and can expose host paths via redirection. Do not add remote-access gateway features without explicit auth, authorization, TLS, logging, and network-boundary design.

### Amazon DCV

The currently documented server is [Amazon DCV 2025.0 build 21744](https://docs.aws.amazon.com/dcv/latest/userguide/doc-history-release-notes.html) (April 1, 2026; Linux server build 20103). The official [Web Client SDK](https://docs.aws.amazon.com/dcv/latest/websdkguide/what-is.html) supports TypeScript/JavaScript embedding for Linux servers and lists files, print, copy/paste, stereo audio, touchscreen/stylus, and multi-monitor. The SDK's [feature table](https://docs.aws.amazon.com/dcv/latest/userguide/client-features.html) caps browser clients at two screens; the detailed [multi-monitor guide](https://docs.aws.amazon.com/dcv/latest/userguide/using-multiple-screens.html) documents default 1920×1080 browser resolution. AWS documents H.264 pixel streaming and software encoding in the [DCV overview](https://docs.aws.amazon.com/dcv/latest/adminguide/what-is-dcv.html) and server requirements.

The key deployment constraint is explicit: the [server matrix](https://docs.aws.amazon.com/dcv/latest/adminguide/servers.html) supports 64-bit ARM only on named EC2 instance families/OS combinations, despite downloadable Ubuntu 24.04 ARM64 packages. The [license guide](https://docs.aws.amazon.com/dcv/latest/adminguide/setting-up-license.html) says non-EC2 installations need a production RLM floating license per concurrent session; automatic evaluation expires after 30 days. Therefore a packaged app that creates local ARM VMs cannot count ARM64 DCV as supported without written vendor confirmation. The Linux setup guide says [Wayland is unsupported](https://docs.aws.amazon.com/dcv/latest/adminguide/setting-up-installing-linux-prereq.html); virtual sessions use Xdcv and can be headless without GPU sharing, while console sessions capture a running Xorg display. A direct SDK integration also needs TLS/certificate, authentication-token, session authorization, and server-port lifecycle design. AWS provides native clients with broader features, but shipping or wrapping those clients is not the same as using its Web SDK.

### RustDesk and PCoIP

RustDesk's [self-host docs](https://rustdesk.com/docs/en/self-host/) describe a two-service rendezvous/relay deployment and differentiate free OSS from Pro features. The [Linux client guide](https://rustdesk.com/docs/en/client/linux/) labels Wayland experimental and says login-screen access needs X11. That architecture is useful for remote support across arbitrary networks; it adds persistent device identity, signaling, relay, public ports, server operations, and client licensing boundaries to a single app-owned VM. No official embeddable client SDK surfaced in the documentation. Treat its self-hosted server as infrastructure, not as a thin stream transport.

The [PCoIP Linux Client SDK guide](https://anyware.hp.com/web-help/pcoip_client_sdk/linux/22.07/) explicitly supports application embedding and lists Ubuntu 18.04 and 20.04. The [23.04 broker example](https://anyware.hp.com/web-help/pcoip_client_sdk/linux/23.04/the_broker_client_example/) is also from 2023. These pages establish that the SDK existed and its intended use; they do not establish availability, current supported OS/architectures, distributable rights, integration with arbitrary local guests, current maintenance, or commercial terms in 2026. Request those exact answers from HP before evaluating it further.

### Commercial full desktop products

[NoMachine's product documentation](https://kb.nomachine.com/AR10K00700) distinguishes shared physical desktops from per-user virtual desktops. Headless Linux can use its embedded X server, but persistent independent virtual desktops require a Terminal Server-family product. Its public knowledge base says sessions survive disconnection and can be reconnected, and Enterprise Desktop is licensed per computer; other tiers cap concurrent sessions. The reviewed public Enterprise Desktop guide is version 8 and lists Ubuntu through 22.04 plus Raspberry Pi ARM variants, so it does not establish current Ubuntu or general ARM64 VM support. The current product pages present downloadable clients/server, not a public client SDK or native-view embedding API. Obtain current OS/architecture support and OEM/redistribution rights from NoMachine before treating this as a product dependency.

[ThinLinc 4.21.0](https://community.thinlinc.com/t/thinlinc-4-21-0-released/2069), released August 21, 2026, adds a native 64-bit ARM Linux client; the vendor's [server requirements answer](https://community.thinlinc.com/t/are-there-any-plans-to-support-arm-architecture-servers/1213) still identifies the server as x86-64-only. Cendio confirms [persistent sessions and concurrent-user licensing](https://community.thinlinc.com/t/how-does-thinlinc-licensing-work/328), and offers free Community Licenses for up to 10 concurrent users without full support. In July 2026, Cendio said [GNOME 50's removal of X11 blocks the current ThinLinc session model and Wayland support is planned](https://community.thinlinc.com/t/thinlinc-4-21-0-beta/2030). This is a useful x86-64 X11 session benchmark, but it does not fit an ARM64-server or GNOME50-Wayland requirement today. No public SDK or embedding right was found in its official downloads/docs.

The current [Parsec hardware/software matrix](https://support.parsec.app/hc/en-us/articles/32381568346644-Hardware-and-Software-Compatibility) says hosting is supported only on Windows and macOS, and its [Linux guide](https://support.parsec.app/hc/en-us/articles/32381552552340-Install-Parsec-App-on-Linux) describes Linux as a client, currently supported on Ubuntu 22.04. It cannot serve a Linux-guest desktop even if its client is attractive as a streaming UX reference.

## Qualification plan before adoption

Build the smallest two-platform tracer using one supported Linux x86-64 guest and one supported Linux ARM64 guest, one fixed desktop and one application launch, with the selected native host client embedded in the actual product UI. Test viewer disconnect/reconnect separately from guest reboot: reconnection should preserve a live session where the platform promises it; after reboot, verify only the documented startup policy and the expected fresh or restored desktop state. For Xpra, add resume after network interruption. Exercise pointer capture/release, host shortcuts, dead keys and CJK IME, text and image clipboard, file transfer policy, audio start/stop, scale-factor changes, resize and fullscreen. Measure idle/active guest RAM, CPU, encode latency, frame rate, and input-to-photon latency under the same repeatable app/scene. Test both a local route and the chosen authenticated remote route. Keep the incumbent implementation as the control; a one-time successful connection does not establish reliability or superiority.
