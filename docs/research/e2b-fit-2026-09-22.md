# E2B fit for Silo, 2026-09-22

## Assessment

Follow-up: the [executed local PoC](e2b-local-poc-2026-09-22.md) now demonstrates
this architecture on an M4 Max, including desktop operation, human takeover,
memory checkpoints and recovery after a clean host shutdown. The source review
below records the preceding assessment; the PoC report contains measurements
and the remaining qualification boundaries.

E2B covers the agent-operated desktop workflow and deserves a direct trial.
Adopting its full runtime changes Silo's host requirements. The user subsequently
accepted an M3-or-newer target for evaluating local E2B while keeping Silo as the
application. With macOS 15+, a nested-virtualization Linux host VM is a documented
route, so local execution is not a reason to reject E2B under that constraint.
Compatibility with Silo's currently published M1/M2 and macOS 14 support is a
separate product decision. This is a source review, not an executed benchmark
or an adoption decision.

## Verified capabilities and boundaries

- [E2B Desktop](https://github.com/e2b-dev/desktop) exposes screenshots, mouse,
  keyboard, application launch, window discovery, file and command operations.
  Its stream can permit user interaction or be view-only. Coordinated human
  takeover, input correctness and Silo's embedded WebKit behavior still need
  application-level qualification.
- The [desktop template](https://github.com/e2b-dev/desktop/blob/main/template/template.py)
  uses Ubuntu 22.04, Xfce/X11, Xvfb, x11vnc and a fork of noVNC with websockify.
  It installs browsers, VS Code and LibreOffice. This is useful implementation
  prior art; it does not establish lower resource use or better reliability.
  Its Chrome and VS Code repositories explicitly target AMD64, so this recipe
  is not a demonstrated unchanged ARM64 desktop image.
- [Persistence](https://docs.e2b.dev/sandbox/persistence) preserves memory and
  filesystem state on pause. Paused sandboxes are documented as retained until
  explicitly killed. The timeout policy must be configured to pause if that is
  intended; its documented default is kill.
- [Snapshots](https://docs.e2b.dev/sandbox/snapshots) capture a checkpoint and
  create new sandboxes from it. They require envd v0.5.0 or newer. Capturing a
  snapshot drops active connections, including WebSockets and PTYs; clients
  must reconnect. Neither checkpointing nor pause reverses external effects.
- The [runtime](https://github.com/e2b-dev/runtime) is Apache-2.0 and includes
  Firecracker orchestration, APIs, template building, proxies and data stores.
  It is a full sandbox platform, not a desktop/viewer package alone.
- [Embed](https://github.com/e2b-dev/runtime/blob/main/embed/README.md) provides
  single-machine Compose, GCP Terraform and Kubernetes packages. They are
  explicitly evaluation packages, not production deployment patterns. Native
  macOS hosting is unsupported; the documented Apple Silicon route needs a
  Linux VM with nested virtualization, M3 or newer and macOS 15 or newer.
- The [Compose requirements](https://github.com/e2b-dev/runtime/blob/main/embed/compose/README.md)
  specify Linux/KVM, a 4 KiB-page kernel, and Linux 6.10+ on ARM64. They recommend
  12 GiB RAM and 20 GiB free disk for the complete installation. These are host
  recommendations, not measured per-sandbox usage or desktop image size.
- [Hosted pricing](https://e2b.dev/pricing), checked September 22: Hobby sessions
  up to one hour; Pro $150/month plus compute, with sessions up to 24 hours.
  Paused-state retention and uninterrupted session duration are different
  limits. Pricing is not a quote for any self-hosted deployment.

Some top-level SDK/marketing pages lag the runtime's Embed documentation.
Use the actual runtime and Embed guides for current self-hosting requirements;
do not describe E2B as cloud-only or as a native macOS runtime.

## Local Mac architecture with the accepted M3+ constraint

Proposed topology: Silo on macOS manages one Linux ARM64 host VM; that VM runs
E2B and its nested Firecracker sandboxes. The outer VM is shared by the local
sandboxes. Silo remains the user-facing application and connects to the local
E2B API and desktop streams. No remote cloud account is inherently required.

[Apple documents nested virtualization on M3 and later](https://developer.apple.com/documentation/virtualization/vzgenericplatformconfiguration/isnestedvirtualizationsupported),
and the E2B Compose requirements explicitly name a Lima or other
Virtualization.framework VM with nested virtualization enabled on macOS 15+.
Provision the outer guest with KVM, a 4 KiB-page ARM64 kernel at version 6.10+
and the other documented host dependencies. Do not infer those capabilities
from the fact that Silo already runs Linux guests: no corresponding E2B, Lima
or nested-virtualization integration was found in the application sources.

Required work is a host-VM lifecycle integration, an E2B backend for Silo's
sandbox operations, local API/stream routing, and an ARM64 desktop recipe.
The documented 12 GiB RAM recommendation and 20 GiB free-disk requirement apply
to the complete Embed host setup, not to each sandbox. Actual idle cost and
desktop workloads need measurement. Embed's evaluation status and reported
bare-metal ARM64 validation do not prove this Mac topology end to end.

### Isolation, storage and CPU architecture

The outer host VM does not replace the per-sandbox VMs. Ten sandboxes mean one
outer Linux VM plus ten Firecracker microVMs. Each microVM is an isolation
boundary; explicit networking or shared resources still define permitted
interactions. The outer VM and E2B services remain a common trust and failure
boundary. Do not describe the arrangement as unconditional complete isolation.

The runtime documents a read-only base image with copy-on-write sandbox roots.
Disk efficiency comes from reusing unchanged image content, not eliminating
per-sandbox VMs. Budget the outer VM, E2B services and caches, base templates,
each sandbox's writes, and retained disk/memory snapshots. A lower total than
Silo's existing storage remains unmeasured.

For a prototype, use Lima's
[VZ driver](https://lima-vm.io/docs/config/vmtype/vz/) with an Ubuntu Server ARM64
guest meeting E2B's kernel requirements. The outer guest needs no graphical
desktop. This is a candidate configuration, not a shipped Silo backend.

AMD64/x86-64 and ARM64/aarch64 are CPU architectures. Apple M-series CPUs use
ARM64. E2B's runtime ARM64 support and the stock desktop template's AMD64 package
choices are separate concerns. Use Linux ARM64 packages throughout the nested
stack; nesting does not translate x86 instructions. For example,
[VS Code publishes Linux ARM64 packages](https://code.visualstudio.com/docs/setup/linux),
so the template's AMD64 repository filter does not mean VS Code lacks ARM
support. Validate the other applications and replace or omit incompatible
packages. Any x86 emulation would be additional, unqualified work.

## Silo comparison and next experiment

The [Silo README](../../README.md) promises local and remote VM management,
including Apple Silicon macOS 14+. The
[backup contract](../SiloUI-RUNTIME-BACKUP-FINDINGS.md#backup-and-restore)
captures stopped-VM disk state and restores a new stopped VM. E2B's documented
memory snapshots provide a capability beyond that contract. Existing
implementation effort is not itself a reason to reject E2B.

Trial one identical workflow: agent downloads a file, edits it in a graphical
application, hands the session to a human, then checkpoints and recovers it.
Measure task completion, reconnect behavior, clipboard/input correctness,
latency, resource use and cost. Use synthetic data. No E2B account, paid
resource, server deployment or live Silo VM was created or modified in this
research.

## Computer-use tools compared with Silo's Luda

Compared E2B's current Desktop SDK sources with Silo's pinned Luda 0.3.4.
These are different integration layers: E2B combines sandbox lifecycle and
streaming with input helpers; Luda exposes desktop operations through MCP and
supplies agent guidance. Neither comparison establishes which agent completes
more tasks.

The [E2B TypeScript implementation](https://github.com/e2b-dev/E2B/blob/main/packages/desktop-js/src/sandbox.ts)
and [Python implementation](https://github.com/e2b-dev/E2B/blob/main/packages/desktop-python/e2b_desktop/main.py)
capture screenshots with `scrot` and send clicks, typing and shortcuts with
`xdotool`. They expose window discovery, application launch and a VNC stream.
The inspected desktop helpers do not expose an accessibility tree, named
control actions, text readback verification or snapshot-bound coordinate
validation. An agent harness can add checks using screenshots, files and
commands. This is a review of those helpers, not every E2B integration.

[Luda's pinned tool reference](https://github.com/0xpolarzero/luda/blob/v0.3.4/docs/TOOLS.md)
adds accessibility inspection, named element actions, targeted text editing
with readback, and coordinate actions bound to recent observations. Checks
have explicit limits: verified selection does not prove activation; dispatched
Save does not prove a saved file; layout checks do not freeze application
content. Accessibility support depends on the application.

For shared human use, Luda documents
[background semantic actions and independent input for qualified GTK3 targets](https://github.com/0xpolarzero/luda/blob/v0.3.4/docs/BACKGROUND-EXPERIENCE.md),
with foreground fallbacks for other targets. This is not universal focus-free
control. Silo's [current integration](../SiloUI-LUDA.md) registers MCP and agent
guidance; its optional browser provider and Editor Bridge are not installed.

Evidence favors retaining the existing integration while testing alternatives,
not claiming a measured reliability advantage. The
[0.3.4 verification](../SiloUI-LUDA-034-VERIFICATION.md) exercised real MCP
observation, Unicode editing, readback and independent saved-file verification.
The [skill benchmark](../SiloUI-LUDA-SKILL-BENCHMARK.md) passed two unchanged
23-case development batches and two real theme tasks after earlier failures.
It was developed against observed failures and is not a held-out comparison
with E2B.

Recommendation: prototype E2B's sandbox lifecycle and viewer while retaining
Luda as the agent-control layer. Running Luda inside an E2B X11 guest is an
integration proposal, not a completed compatibility test; provide its Python
and session dependencies in a custom template. Compare native E2B helpers and
Luda with the same model, applications and tasks, measuring independently
verified completion, false completion, latency and human takeover. E2B's
smaller screenshot/input interface is a credible alternative for a model
trained around that interaction pattern; richer tools alone do not establish
better results.

Follow-up: the [Codex native interface comparison](codex-e2b-luda-computer-use-2026-09-22.md)
found accessibility targeting with screenshot fallbacks in the installed Codex
tool contract. The next control experiment should include a small screenshot
baseline and a compact hybrid interface alongside current Luda. Keeping Luda
available during an infrastructure trial is not evidence for selecting it as
the final control layer.
