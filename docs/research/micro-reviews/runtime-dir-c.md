# Runtime directory micro-review: runtime-dir-c

Scope: the last five of fourteen files sorted by relative path under `app/SiloUI/src-tauri/src/runtime/`: `remote_ops.rs`, `shutdown.rs`, `storage.rs`, `storage/tests.rs`, and `update_recovery.rs`. Read-only source review; no builds, tests, or live runtime operations. Checked the first, second, and repository pass-three review reports for existing findings.

## runtime-dir-c-1 — P2 — Update preparation omits running, uncommitted VMs

- **Location:** `app/SiloUI/src-tauri/src/runtime/update_recovery.rs:106`, `:112`, `:174`.
- **Trigger:** VM creation leaves a running runtime VM before its metadata commit, and cleanup fails or the process is interrupted. Its immutable identity remains in the configuration-recovery journal. Install an update before retrying that configuration.
- **Evidence:** `running()` returns an empty set when metadata is absent and otherwise visits only committed metadata machines. It never reads `configuration_recovery::shutdown_machines()` or checks the complete managed runtime inventory. `prepare()` stops only the resulting set. This state is explicitly supported by `shutdown.rs:117` and its `quit_stops_created_vms_when_guest_verification_failed_before_metadata_commit` test: Quit merges the configuration journal and stops those exact uncommitted identities. In `runtime.rs`, `create_machine_with_progress()` runs guest preparation before the caller publishes metadata; failed cleanup can preserve the VM. Both updater installation paths call `prepare()` without checking for an unfinished configuration journal.
- **Consequence:** Update confirmation omits that running VM, and installation proceeds without stopping it. The update-resume journal also omits it. The app replaces its bundled runtime while that Silo-owned VM remains running, violating the update shutdown contract. This review does not establish disk corruption.
- **Suggested fix:** Refuse installation with an actionable configuration-recovery error when a journal-owned runtime VM exists outside committed metadata, or explicitly include and safely stop those identities. Check managed inventory before treating absent metadata as an empty running set; preserve the unfinished configuration rather than replaying setup.
- **Regression test:** Reuse the shutdown fixture with absent metadata, a pending configuration journal, and an exact matching running VM. Update preparation must refuse before installation or stop that VM after consent; it must never return successful preparation with the VM still running. Repeat with another committed VM so the defect cannot be fixed only for first setup.

## runtime-dir-c-2 — P2 — Failed restore is reported as zero disk usage

- **Location:** `app/SiloUI/src-tauri/src/runtime/storage.rs:756`, `:772`, `:778`.
- **Trigger:** Starting a fork or imported checkpoint creates its runtime VM and disks, then fails verification or is interrupted before clearing `pending_checkpoint_restore`. Open Storage for that sandbox after the attempt ends.
- **Evidence:** The command uses `checkpoints::is_pending()`, which checks only whether `pending_checkpoint_restore` exists (`checkpoints.rs:757`). It immediately returns both host disk totals as `Some(0)` and clears `last_error`, without inspecting the runtime. `start_pending()` persists `restore_attempted` before the restore and retains the pending record on failure (`checkpoints.rs:1175`, `:1266`), including attempts observed Running, Paused, or Crashed. The established `pending_view()` explicitly distinguishes this state: a runtime VM present after an attempted restore is a present workspace, even while its pending record survives (`checkpoints.rs:765`). `update_recovery.rs:115` already uses that distinction.
- **Consequence:** Storage reports 0 B for allocated workspace and runtime disks and suppresses the stored maintenance error. Reclaim also reports “Start … first” even when the failed attempt left the VM running. Users cannot see the actual disk footprint of the preserved failed attempt.
- **Suggested fix:** Resolve runtime presence with the existing pending-view rules before returning the absent-workspace response. Measure a present VM's disks after verifying its identity. If recovery still prevents reclamation, report the unfinished restore accurately and retain diagnostic errors.
- **Regression test:** Supply a configured sandbox with a pending checkpoint, `restore_attempted = true`, matching runtime identity, and nonempty workspace/root disks. A Storage read must return their measured allocation and retain errors for both Running and Stopped attempts. An unattempted pending sandbox with no runtime VM must still report zero allocation without starting a VM.
