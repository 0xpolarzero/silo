# Independent review: D2 upstream report claim

Date: 2026-09-23. Scope: read-only review of the [D2 report draft](e2b-d2-report-readiness-2026-09-23.md), [source-built receipt](e2b-d2-rootfs-sync-repro-2026-09-23.md), its ignored raw JSON receipts, the [historical error audit](e2b-d2-error-audit-2026-09-23.md), the diagnostic patch, and the captured source. No VM or service was touched.

**Verdict: keep the current draft unpublished.** The source-built experiment establishes a reproducible **SDK recovery failure after a synthetic Go sync error** on the tested destroy-path candidate. It does not establish destruction of every copy of the latest state, a physical EIO mechanism, a violation of an upstream documented failure guarantee, or the exact historical release's behavior. A scoped upstream question or issue about this candidate can become defensible after its claim is narrowed and the runnable evidence is packaged. An incident-attributed bug is still blocked by [release-source mapping](e2b-release-source-mapping-2026-09-23.md).

## Findings that change the claim

1. **“Original-state loss” is stronger than the oracle measured.** The armed run `5ca23681b9ae451da8c713b8e5ea9837` acknowledged a process nonce and guest-fsynced file hash, then `pause()` returned 500. The immediate attempted oracle read recorded `TimeoutException`; passive `get_info`, run-tagged list and later exact `connect` returned no original. Create-from-failed-snapshot returned 404, no matching Firecracker process was found, and the inspected build paths were empty about two minutes later. Those independent observations prove no *tested SDK-supported* path restored the acknowledged state. They do not inspect every backing COW/cache object, retention copy, or forensic recovery path at failure time. The failed snapshot's 404 is expected if its diff was invalid; it should not be promoted as a valid checkpoint solely to improve discoverability. [Raw SDK receipt](../../app/SiloUI/src-tauri/target/verification/e2b-local/deployments/diagnostic-d1/evidence/d2-source-fault/5ca23681b9ae451da8c713b8e5ea9837-sdk-recovery.json), [after-inspection receipt](../../app/SiloUI/src-tauri/target/verification/e2b-local/deployments/diagnostic-d1/evidence/d2-source-fault/5ca23681b9ae451da8c713b8e5ea9837-after.json).
2. **The hook validates a Go branch, not physical EIO equivalence.** The patch calls `CloseToDiffWithSyncEIO` in the synchronous destroy path; that method substitutes `PathError(EIO)` for `File.Sync`. The control passed and the trigger fired once, so the experiment credibly traces teardown and API cleanup after *that return value*. A real `File.Sync` EIO can reflect earlier writeback failure or a damaged backing filesystem. The synthetic run leaves the real file's flush, cache health, and feasibility of retaining a recoverable object untested. The proposed “preserve the ejected cache” design is therefore a hypothesis, not evidence that latest state could survive the historical fault. [Patch](../../experiments/e2b-local/patches/d2-rootfs-sync-eio-exact-id.patch), [captured `CloseToDiff`](../../app/SiloUI/src-tauri/target/verification/e2b-local/upstream/full/runtime-a065a4ddb3f2c6a4149634d9acb14b62f65839ac/packages/orchestrator/pkg/sandbox/build/local_diff.go).
3. **The teardown sequence is real on this candidate, but its classification is conditional.** Captured `Server.Pause` marks the sandbox stopping and defers stop before `snapshotAndCacheSandbox`. The destroy-path NBD exporter ejects the writable cache, closes the sandbox and waits for device release before diff sync; the direct exporter also stops it before export. `CloseToDiff` removes a partial diff after sync error. The API removes the original record on the generic failure. This explains the observed unaddressability without blaming the Silo adapter. It also means “just keep the old VM running” is not a tested repair. Whether a failed pause must preserve an addressable source is a required **Silo** invariant; the [Python SDK source](https://github.com/e2b-dev/E2B/blob/main/packages/python-sdk/e2b/sandbox_sync/main.py) documents success and connect behavior, but the cited text does not promise recovery after pause fails. Do not call that upstream contract violation without an upstream guarantee or maintainer agreement. [Captured lifecycle audit](e2b-lifecycle-source-audit-2026-09-23.md).
4. **Historical attribution is still open.** The 2026-09-22 log shows a stopped lifecycle before a rootfs sync EIO, but it is not a syscall/device trace. The diagnostic source build resolves two dependencies differently from the pinned release; the public commit URL using the release suffix returns 404, and effective flags are unrecorded. Matching binary call targets support structural similarity, not the exact source, flags or branch for the incident. The draft's separate historical/candidate labels are correct and must remain on every public statement. [Provenance audit](e2b-provenance-audit-2026-09-23.md), [historical audit](e2b-d2-error-audit-2026-09-23.md).

## Falsifiable report threshold

For a **source-built candidate issue**, state: “On captured tree manifest `f10d3785…`, a one-shot synthetic `PathError(EIO)` at the destroy-path rootfs diff sync boundary made `pause()` fail after source stop; the tested SDK `get_info`, `connect`, and create-from-failed-snapshot paths could not recover two acknowledged oracles.” Include the patch, exact run/control IDs, source and binary hashes, API/node error correlation, and the tested recovery calls. State that no comprehensive byte-loss claim or physical EIO claim follows. Confirm the maintainers' intended failure contract before labeling this an upstream bug rather than an API recovery/design limitation.

For an **incident-attributed bug**, additionally obtain the incident-linked API/orchestrator artifact-to-source mapping and effective flags, reproduce an actual `fsync`/`fdatasync` failure on a bounded owned filesystem, and inventory the ejected cache plus all referenced local/canonical objects *before* cleanup. A preservation fix must restore the newly acknowledged file and process nonce through a supported path after that fault; it must also fail honestly when backing storage cannot preserve those bytes.

**Next action:** narrow the public claim to tested SDK unaddressability, then run the bounded actual-sync fault with pre-cleanup artifact inventory before proposing a preservation fix.
