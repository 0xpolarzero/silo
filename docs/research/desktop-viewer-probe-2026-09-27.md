## Sandbox deletion lock diagnosis

- Source confirms a deterministic contention path. The native Linux desktop viewer calls `read_desktop_state` on open and every five seconds (`app/SiloUI/src/desktop/linux-desktop-viewer.tsx:101-115`). That command runs `desktop::local`, which takes the process-wide `runtime::MUTATION_LOCK` with `try_lock` and holds it through `status_with` (`app/SiloUI/src-tauri/src/desktop.rs:385-389,419-450`). For a running VM, `status_with` inspects the VM and invokes the guest `silo-desktop status` script through MicroSandbox exec with a 15-second timeout (`desktop.rs:215-234`).
- Local deletion removes a VM from the UI's displayed local-machine list and submits the full remaining list (`app/SiloUI/src/features/application/pages/overview-page.tsx:266-273`). The app shows that candidate as applying immediately (`application-app.tsx:172-183`); production setup eventually calls `save_machine_configuration` (`app/SiloUI/src/desktop/production-source.ts:668-695`), whose backend tries the same global lock without waiting and returns `RuntimeError::Busy` on contention (`app/SiloUI/src-tauri/src/runtime.rs:2170-2187`). The frontend retains that failure as `sandboxConfigurationOperation.status === "failed"`; Overview displays it and keeps the machine list disabled, including Add, until dismissal or a successful configuration (`overview-page.tsx:233-254,281`; `production-source.ts:988-995`). Existing test `production-source.test.ts:883-899` verifies retained-error and dismissal behavior for another preflight failure.
- A desktop status poll overlapping the delete request is a source-supported ordering that produces the observed busy error and persistent “Sandbox changes failed” screen. ### Local runtime queue boundary

The queue requested for lifecycle work belongs to one owning Silo process and its active local runtime home. Route Silo-managed runtime-changing intents through that one queue: workspace start/stop/restart and configuration add/edit/delete; checkpoint create/fork/restore; backup and restore; storage reclaim; local desktop actions; VM-facing GitHub and secret policy application; SSH listener/access changes; published-port reconciliation/control; repository push; and runtime recovery, shutdown, or update steps that inspect, stop, replace, or resume those VMs. A queued operation must resolve its target by stable VM ID and read current metadata when it reaches the front. In particular, do not queue the existing whole-configuration delete candidate: it is a stale snapshot and can omit a fork committed while it waited. The queue can order Silo-initiated work; it cannot serialize arbitrary commands in an already-open guest shell, exported SSH session, external runtime CLI, or a different Silo host.

Read paths should not wait for the writer. Metadata, settings, account/catalog state, files, logs, and ordinary status observations can read committed state independently; live VM observations should mark themselves stale or discard/retry when they overlap a queued mutation. Split reconciliation from observation where a nominal read has effects: `network::read_network_state` calls `observe`, which can add/remove live port forwarding (`network.rs:272-350,530-565`); `ssh_access::read_ssh_access_state` takes the runtime mutex and calls `reconcile` (`ssh_access.rs:439-447`). The desktop status poll holds the mutation lock through guest status (`desktop.rs:382-426`), while directory listing issues a read-only guest `exec --no-start` (`files.rs:149-175`) and should remain an observation that can report stale or retry after overlap, not queue as a writer.

Keep subsystem locks that protect state separate from the runtime queue: application preferences and shutdown-flush state (`settings.rs:470-515`); GitHub credential, intent, account, catalog, and policy documents (`github.rs:23-95`, `github_personal_token.rs:10-14`); secret references and credential-vault cache (`secrets.rs:15-18`); port configuration (`network.rs:15`); SSH listener ownership (`ssh_access.rs:65`); backup journal/view/cancellation (`backup_controller.rs:190-195`); updater state and install admission (`updates.rs:18,55`); host-push idempotency records (`host_push_operations.rs:15-17`); remote host configuration and request transport (`remote.rs:21-22`); and viewer/tunnel/snapshot/log caches (`desktop_viewer.rs:29`, `remote_network.rs:26`, `files.rs:39`, `runtime_logs.rs:69`). Host-side OAuth, keychain writes, GitHub catalog HTTP, secret-value storage, app preferences, and remote-host preferences remain outside the VM queue. Their later writes into guests must enter it: GitHub/secret policy application already goes through runtime entry points that take the mutation lock (`runtime.rs:1127,1194,1486,5631`). Startup owns a separate once-at-a-time gate and delegates actual lifecycle actions to the normal runtime action path (`startup.rs:103+`). Migration builds a staged runtime generation while ordinary operations are gated (`runtime_migration.rs:578-620`).

Do not remove the cross-process MicroSandbox command fence. `configuration_recovery::command_lock` takes an OS `flock`, passes its descriptor to the child, and retains it until the child exits; `run_msb_process` currently applies it to `create`, `modify`, `remove`, `stop`, `restore`, and `adopt-disk` (`runtime.rs:728-733`, `runtime/configuration_recovery.rs:278-307`). Storage reclamation independently takes the same file lock before opening/changing the workspace disk (`runtime/storage.rs:213`). The in-process queue cannot serialize another Silo process or a direct runtime invocation. Remote requests must enter the owner Silo's queue; `remote::REQUEST_LOCK` currently serializes acceptance and execution of recorded operations (`remote.rs:802-817`), while `recorded_operation` preserves accept-once/no-replay behavior (`:892-919`). Let the owner queue serialize execution, but retain that journal contract. Keep those boundaries explicit; the proposed queue is not an app-wide queue.

The current queue coverage is incomplete: local port forwarding can control a running guest under only `NETWORK_LOCK` and may race with stop/remove; `network` and `ssh_access` read/reconcile paths also have live side effects and must use the owner queue; and `desktop.status` is incorrectly coupled to the long writer lock. Read-only directory listing uses runtime `exec` outside the queue and should stay outside as an observation with overlap handling. The design target is one local-runtime writer queue with all Silo-managed VM side effects routed through it, plus direct committed-state reads and separate host-state locks. This is an ownership-boundary refactor, not a new scheduler per VM. Keep operation intents fresh at execution time, split queued internals from public queue entry points to avoid nested enqueue/deadlock, and retain file locks and subsystem state mutexes for their distinct invariants.
