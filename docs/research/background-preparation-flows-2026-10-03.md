# Background preparation flows: verified facts (2026-10-03)

Paths are relative to `app/SiloUI/src-tauri/src/` (Rust) or `app/SiloUI/src/` (frontend). Read-only investigation of the code and of the Dev build's data (`~/Library/Application Support/org.silo.dev`, state dir `~/.silo-dev`).

## 1. VM image import

- Verified: the import is `guest_image::prepare` (`guest_image.rs:382`), called from `RuntimeRunner::prepare_guest_image` (`runtime.rs:271`), from `create_machine_with_progress` (`runtime.rs:5418`, inside the computer-wide MachineConfiguration gate) and from a test helper in `secrets_runtime.rs:1095`. It needs only `RuntimePaths` (`guest_image` resource dir, `home` = MSB_HOME, `executable`, `library`): validate bundle, open `GlobalCache::new(home/cache)`, unpack the .tar.gz to a temp file in the cache tmp dir (needs 4x unpacked bytes free, `guest_image.rs:400`), then `msb image load --input <tar> --tag <ref> --quiet` (300 s timeout) and re-verify.
- Verified: nothing per-sandbox. The image is keyed by `manifest.image_reference`; the sandbox name only appears in progress events.
- Detection of "already imported": `cached(&cache, &manifest)` (`guest_image.rs:~330-345`) checks fsmeta, vmdk and all layers materialized in the global cache; if true it returns the reference with no load. First create therefore does the ~1 min import; later ones are instant.
- Concurrency: only an in-process `static IMPORT_LOCK: Mutex<()>` (`guest_image.rs:16`). No cross-process lock. `image load` does not take the runtime worker lock (`takes_worker_lock`, `runtime.rs:1423`, lists only create/modify/remove/stop/restore/adopt-disk). A second Silo process would race (single_instance.rs exists, so low risk).
- Progress: only `SetupRunner` (`runtime.rs:965-990`) emits `workspace-image-import` (fraction 0, no sub-progress), because it matches args `image load`. Outside create nothing emits it.
- Launch feasibility: verified possible in principle (needs only `runtime_paths(app)`, `runtime.rs:741`, which is refused while a storage migration runs, and `ensure_runtime_files`). Startup already has a post-recovery blocking task (`startup.rs:157-272`) and calls `image_cache::repair` there (`startup.rs:185`). Unknown: whether `msb image load` touches the sqlite DB in a way that conflicts with a concurrent create (not checked in msb source).
- Implication: add an app-start "prepare image" task that reuses `guest_image::prepare` with a progress publisher; make create call the same function and, if one is in flight, wait on it (IMPORT_LOCK already serializes; add status so the wait is visible). Do not hold the computer gate during the import at launch, or every lifecycle op queues behind it for a minute.

## 2. LCU archive

- Verified: guest helper `archive_path` (`guest/silo-computer-use.py:334`) uses the image-staged archive `/usr/local/share/silo/lcu/<name>` only if its sha256 matches the lock, else `download()` via curl with 5 attempts, 240 s each, 420 s budget (`:87-90`, `:302`). Docs confirm the published v4 image stages 0.8.1 while the lock is 0.8.8 (`docs/SiloUI-GUEST-IMAGES.md:204`); `scripts/build-guest-image.mjs:12-40` stages whatever `guest/lcu-lock.json` says at image build time. Host side already holds the url+sha256 (`computer_use::pinned`, `computer_use.rs:737`) and passes it into the guest in `/var/lib/silo-computer-use/pinned.json` (`guest_script`, `:761`).
- Verified: a host-lent read-only mount is the existing pattern: `mount_spec` `<dir>:/opt/silo/chatgpt:ro,uid=0,gid=0` (`computer_use.rs:661`), added via `msb create ... -v` in `mount_args` (`:669`, spliced at `runtime.rs:5460-5466`) and again for restore (`runtime/checkpoints.rs:1120`).
- Mount timing: verified only at create and restore. `msb modify` as Silo calls it only sets cpus/memory/labels/secret (`runtime.rs:2463`, `:5770`); `require_mount`/`mount_present` (`checkpoints.rs:1101`, `computer_use.rs:690`) show existing sandboxes are expected to already carry the mount. Unknown: whether upstream `msb modify` can add `-v`. Silo never does it, so assume a new mount needs recreation, which would be unacceptable for existing sandboxes.
- Alternative that avoids a new mount: put the LCU archive inside the already mounted folder. Verified the folder is `<app data>/chatgpt/published` and holds version dirs plus `.published.json` records, with garbage collection of other versions (`chatgpt_app.rs:1833`) and a strict tree digest (`verify_published`); an LCU tarball there would need the digest/GC code extended and the guest helper to look under `/opt/silo/chatgpt/`. Unknown: how `lcu` treats extra files beside the app dir (LCU refuses non-root-owned app folders, per the `mount_spec` comment).
- Implication: for new sandboxes, a second read-only mount (or a file in the published folder) is feasible; for existing ones only the in-guest download remains. Simplest high-value step: a new image whose staged archive matches the lock removes the download for everyone created after it.

## 3. Creation boot

- Verified: create boots the VM temporarily twice. `verify_guest_tools` (`runtime.rs:5320-5340`, `msb exec` of `verify-tools.sh`, then confirms stopped) and, for desktop VMs, `desktop::configure_with` at step `desktop-installation` (`runtime.rs:5496-5506`). Both use the `exec` temporary-boot path (`runtime.rs:1096-1175`): `msb start`, `working_account::prepare(&Booted,...)`, run command, `msb stop`. Dev log confirms: `e2e-cu1/logs/exec.log` shows start 12:11:04Z (verify tools: git/gh/lfs versions, stopped 12:11:05), start 12:11:06Z (desktop: "Using the desktop preinstalled in the guest image", stopped 12:11:08Z).
- Mounts during that boot: the sandbox was created with `mount_args` mounts (`runtime.rs:5379`), so the ChatGPT folder is mounted (read-only) in those boots whenever it existed at create time. `mount_args` only requires the folder to exist, not to be filled (`computer_use.rs:669-685`, comment "a VM must not wait for it"). In the Dev data the app was published 12:10Z, before the 12:11Z create.
- `prepare_booted` / `computer_use::after_boot` runs only on the `start`/`restart` branch and after `restore` (`runtime.rs:1105`, `:1181`), not in the `exec` temporary-boot branch. So computer-use apply does not run during creation; creation ends with `computer_use::start_with` (`runtime.rs:5508`), which only writes the initial approval policy. First apply happens on the user's first start. Dev evidence: apply result recorded at 14:38:07 local right after the first user start at 14:37:54 (`lifecycle-operations` journal and `computer-use/<id>.json` `last.at`).
- Feasibility: adding apply into creation is possible between desktop install and the final stop: `run_helper` (`computer_use.rs:824`) just execs `guest_script(pinned, apply_command(...))` through a runner; it needs a running VM and the mounted app. Unknown: `lcu setup` needs the desktop session (`session_wait` constants `SESSION_WAIT_BOOT = 300`, helper header lines 10-20) so it must run with the desktop service up, not in the bare `exec` boots. Creation would need one extra deliberate start under the create operation.
- Folder not yet published: the app downloads at app start via `start_automatic` (`chatgpt_app.rs:2216`, after `auto::START_DELAY`) and the mount is of an empty `published` dir. Status stream exists: `Status::{Idle,Downloading{received,total},Verifying,Extracting,Ready,Failed}` (`chatgpt_app.rs:188`), cached in `cached_status()` and emitted as `chatgpt-app-status` (`:1959`, `publish`). Creation could poll `cached_status()` / the event until `Ready` (the `ensure()` call holds a root lock, `chatgpt_app.rs:1560`). Verified hazard: `mount_args` avoids waiting on that lock deliberately (`register_published_now`), because waiting under the computer gate stalls every lifecycle op and Quit (comment at `chatgpt_app.rs:~2020`).
- Implication: creation can wait on ChatGPT readiness, but must not block while holding the computer gate; do the wait before acquiring, or as a visible step of the create toast without the gate. The mount already works with an empty folder, so a created VM can safely be finished later: the host `app_ready` hook (`computer_use.rs:1265`) already re-applies on running VMs when the app becomes ready.

## 4. Operation queue and toasts

- Verified: gate in `runtime/operation_gate.rs`: scopes `Computer` (conflicts with everything) and `Vm{id}` (`:19-36`); kinds include Lifecycle, MachineConfiguration, Other (`:72-92`); entries have `label`, `kind`, `vmId`, `cancellable`, `expectedMs`, `blockedByHidden` (`:96-120`). `labelled()` (`:1104`) temporarily relabels the running entry, used for the account setup step (`working_account.rs:58-62`).
- No notion of a background preparation as a blocker: image import, ChatGPT download and LCU download are not gate entries (ChatGPT worker deliberately avoids the gate, `chatgpt_app.rs:2033+`). Only "Setting up computer use in X" is a gate entry (kind Other, VM scope).
- Frontend: queue entries become row text via `waitingStatusText` = `Waiting for <labels>…` (`features/application/model/operation-queue.ts:184`). Kinds with their own toast are skipped by `toastableQueue` (`:75-103`). Lifecycle toast: `use-lifecycle-toasts.tsx` shows step "Starting…" or the waiting text only after 800 ms (`LIFECYCLE_TOAST_DELAY_MS`); the step does not follow `labelled()` of the running entry. Creation toast: `machine-configuration-toast.tsx` calls `showOperationProgress("machine-configuration", {title, step, progress, ...})` driven by `describeConfiguration` (`model/machine-configuration-progress.ts`) which maps backend `step` ids (`workspace-image-import`, `desktop-installation`, ...) to text and 5 stages; progress events come from `machine_progress` (`runtime.rs:3370-3395`) into `operation.progressEvents`. `showOperationProgress` already accepts `steps` (`lib/operation-toast.ts:12-20`).
- Implication: a waiting-on-preparation step is easiest as (a) a new backend `preparations` snapshot (image, chatgpt, lcu) with the same fraction/status shape as `chatgpt-app-status`, merged by the frontend into the step text of the action's toast (create and start), rather than as gate entries (a gate entry would block the Computer scope). Add stages to `creationStage`.

## 5. Start flow

- Path: UI `start` -> `lifecycle` command (`runtime.rs:~3140-3290`): `resolve_vm_id`, acquires `OPERATIONS.kind(Lifecycle)` scoped to the VM with key `vm:<id>:start` (a Computer-scope op in flight, e.g. configuration or storage maintenance, makes it wait), `gated_auto_retry`, `explicit_workspace_action_with` -> `lifecycle_recovery::perform` -> `run_msb_with_progress("start")` (`runtime.rs:1068`) which takes `lock_vm_runtime` (waits for live access changes), runs `msb start` (expected 180 s), then `network::reconcile_started`, `ssh_access::reconcile`, `prepare_booted` (account check; first-time account setup relabels the entry, `working_account.rs:58`), then spawns `computer_use::after_boot` on a thread (`runtime.rs:1221`), which takes a separate VM-scope gate turn labelled "Setting up computer use in X" (`computer_use.rs:1144-1165`, up to 15 min `APPLY_TIMEOUT`, 10 min `GATE_WAIT`). A user stop/restart preempts it (`Preempt`, `:972`).
- Why "stopped, nothing happening, then suddenly started": code comment at `runtime.rs:~3205` says no state event is emitted while the gate is held, so the row keeps its last state until the post-release `application-state-changed`. The frontend sets `lifecycleAction` itself from `pendingLifecycle` (`desktop/production-source.ts:1209, 748`), but the toast only appears after 800 ms and its step is static "Starting…". Also the start only returns after `msb start` + account check + network/ssh reconcile + prepare_booted, so any wait on the gate or `lock_vm_runtime` shows no text beyond "Starting…". Local guess, not proven from the UI.
- Dev log (most recent start, VM `e2e-cu1`, id f7e83b3b…), times are UTC in runtime logs (local = +2 h):
  - 14:37:54 local: lifecycle journal start recorded (`lifecycle-operations`/`sandbox-activity.json` timestamp 1791031074733).
  - 12:37:54.867Z `sandbox starting`; 12:37:54.975 `entering VM`; 12:37:55.203 `received core.ready from agentd` (VM ready in ~0.4 s, so the state flip was not delayed by `msb start`).
  - 12:37:57.293 first exec output "ready" (working-account check `ready`), then several `/proc/net/tcp` dumps 12:37:57.8 (ssh/network reconcile) and a further one at 12:38:06.85.
  - 12:38:07.873 apply helper returns: `{"apply": {"approval":"ask","outcome":"applied"}, "lcuVersion": ...}`; `computer-use/<id>.json` records `last.at` 1791031087 = 12:38:07Z. Total ~13 s from start to apply done, no LCU download visible (`exec.log` has no "downloading" lines), `lcuVersion` 0.8.8 already installed. Host log was in `microsandbox/sandboxes/e2e-cu1/logs/{runtime,exec,kernel}.log`; Silo's own stderr is not persisted anywhere I could find (no `Logs/org.silo.dev`), so host-side gate waits for this start cannot be reconstructed. Unknown: the exact UI timing the user saw.
- Implication: the log shows the backend itself is fast for this case; the perceived gap is a lack of visible state/step on the host side (no event between click and release), so the design should emit progress steps (booting, account, network, computer use) and show the toast immediately for lifecycle start.

## 6. "Setting up computer use"

- Verified: the only occurrence is the backend constant `SYNC_LABEL = "Setting up computer use in"` (`computer_use.rs:965`), formatted `"{SYNC_LABEL} {name}"` (`:1159`) as the label of the VM-scope Other-kind gate entry that wraps one apply turn (`apply_once`). It appears in the operation queue panel (`features/application/components/operation-queue-panel.tsx`) for as long as the entry runs and in other operations' wait text (`Waiting for Setting up computer use in X…`). Frontend has no literal for it (only `desktop/linux-desktop-viewer.tsx:41` "Setting up LCU…" for `lcuState === "installing"`, and the desktop panel states `preparing`/`installing` from `computer_use_state`, `computer_use.rs:1390-1515`, e.g. "Waiting to download ChatGPT for Linux", "Preparing ChatGPT for Linux", "Waiting for the ChatGPT folder inside the sandbox", "Computer use is not set up yet. Silo sets it up at each start.").
- States: queue entry exists while the guest helper runs after every boot (Trigger::Boot always runs the helper, cheap if nothing to do), when the user changes the approval switch (Trigger::Change), at app start for unfinished attempts (`reconcile`), and when the ChatGPT app becomes ready (`app_ready`, called from `chatgpt_app.rs:2185`). Not shown during creation (no apply there).
- Implication: if apply moves into creation or is made a visible step, reuse this label as the step text of the owning toast instead of a free-standing queue entry.
