Silo Help

Silo runs Linux development sandboxes on macOS and Linux. A sandbox has its own operating system, files, and resources. Its workspace is the /workspace folder and disk. Sandbox disks remain separate from the Silo application.

Sandboxes and the sandbox page

Use Add above the sandbox list to create a sandbox, connect a computer, or choose Import sandbox…. Choose a sandbox's name to open its page. Drag a sandbox by its handle, or focus the handle and press the arrow keys, to change its place in the list. This computer keeps its own order, for its sandboxes and those on other computers; sandboxes that need attention stay at the top. The page header provides Terminal, Editor, and start or stop controls. Stopping or restarting a running sandbox asks for confirmation.

The sandbox page has an Overview tab for settings, secrets, and ports; Checkpoints for saved checkpoints; Storage for local disk usage; and SSH for supported sandbox connections. Tabs appear only when the sandbox supports them. An SSH host is a computer you connect to over SSH, rather than a sandbox Silo creates and manages.

Use the sandbox's actions menu to edit its settings in place. Duplicate settings creates a new empty sandbox with the same settings. Fork… creates a new sandbox with a copy of this one's files, starting from its current state. A fork is stopped until you start it. CPU and memory edits stop a running sandbox and apply on its next start. Existing sandbox names and disk sizes cannot change.

Delete… asks you to confirm permanent deletion and explains which files and checkpoints will be removed. Stop a running sandbox first. Where offered, Export, then delete saves and verifies an export file before deleting the sandbox. Delete permanently deletes it without an export.

Overview: secrets and ports

The sandbox page's Overview tab shows its settings, assigned secrets, and ports. Manage credentials in Secrets and choose which sandboxes and HTTPS domains can use them. GitHub repository access and Git identity are configured in GitHub. Check the operation result; Silo tells you when a change requires a restart.

Network shows ports across sandboxes. In every browser, including Safari, a website port opens at an address of its own sandbox, such as http://dev-1a2b3c4d.localhost:43000, so its cookies stay separate from other local services and sandboxes. Use Copy 127.0.0.1 address for development servers that reject other host names. A sandbox website can still send requests to other services on this computer, so open it only when you trust its code.

Checkpoints, Fork, and Restore

Open the sandbox page's Checkpoints tab. New checkpoint captures its current session and disks. Restore rewinds the same sandbox to a checkpoint after saving a recovery checkpoint. It leaves the sandbox stopped. Restore does not undo changes outside the sandbox, such as pushed commits or sent requests.

Use a checkpoint's actions menu to choose Fork… and create a new stopped sandbox with a copy of its files, or Export… to save a local checkpoint to an export file. Checkpoint history remains on the computer that owns the sandbox.

Delete checkpoint data through Delete… in the checkpoint's actions menu, then confirm. A checkpoint that another sandbox depends on cannot be deleted yet. Deleting a sandbox removes checkpoint data that nothing else needs; data needed by a fork stays until its last dependent sandbox is deleted. The Storage tab shows checkpoint disk usage.

Export and Import

Choose Export… from a local sandbox's actions menu and pick a folder to save a .silo-backup export file containing its disks. A running sandbox keeps running. Checkpoint history is not included. Import creates a new stopped sandbox from the exported disks, without the captured memory session.

Choose Add then Import sandbox… above the sandbox list, or File → Import Sandbox… in the application menu. Select an export file; Silo verifies it and asks for a sandbox name. Import does not replace an existing sandbox. Keep export files off the owning computer for another copy, or import one on another compatible computer to move your work.

Storage and files

Open a local sandbox's Storage tab to compare workspace space allocated on this computer with space used inside the sandbox. Workspace storage holds /workspace; runtime storage holds the operating system and installed tools. Deleted workspace files can leave unused space allocated in the disk image. Start the sandbox and use Reclaim unused space to release it without deleting files. Reclamation shrinks the workspace disk, not the runtime disk or checkpoints. If Silo asks for a restart, restart before reclaiming.

Silo also reclaims automatically after seven days since the last success, and before a normal stop when the last success was at least 24 hours ago. A sandbox without a previous successful reclaim is eligible on its next start. Failed automatic attempts wait at least 24 hours before retrying. Quit gives reclamation a shared 15-second command budget across local sandboxes; a failed reclaim does not prevent normal shutdown.

After an upgrade that converts your sandboxes to new storage, Silo keeps the previous storage as a pre-upgrade backup in case something looks wrong. The migration screen shows its size and the date Silo deletes it automatically, 14 days after the upgrade. Open Settings → General → Storage to see it again: Show reveals the folder in your file manager, and Delete now deletes it permanently after you confirm. The folder holds Linux disk images, so you can copy it elsewhere but not browse files in it. Downgrading to an earlier Silo is not supported. The backup is deleted only after every sandbox was converted; if you chose to continue after a failed migration, Silo keeps the original sandbox data and never deletes it.

Files browses sandbox directories. Start the sandbox before browsing its files.

SSH access

Open the sandbox page's SSH tab, from its ⋯ menu or by clicking its SSH badge, to review connections and authorized keys. SSH from the owning computer and SSH from other computers are separate settings. Allow SSH from other computers exposes the selected address and port to that network and asks for confirmation. Only authorized keys can sign in. Use Copy terminal command or Save key file in the connection's actions menu. A downloaded key file is private; keep it secure.

Linux desktop

Select Linux desktop when creating a sandbox, or choose Add Linux desktop from an existing sandbox's actions menu. Installation adds Xfce to the same Ubuntu sandbox; files and terminal tools stay in place. Desktop packages remain installed.

Start desktop with sandbox is on by default. Turn it off to start the desktop explicitly from its viewer. Turning it off leaves an existing session running. Stopping the sandbox always stops its desktop. An explicit desktop stop lasts until you start it again or the sandbox next starts with automatic startup enabled.

Open Linux desktop opens the interactive viewer. Closing the viewer leaves applications running. Stopping or restarting the desktop closes graphical applications, so save your work first. Independent terminal jobs continue. Install additional Linux applications from the desktop terminal; the silo account has passwordless sudo.

Adding a Linux desktop does not install agent tools. LCU is the supported computer-use integration: choose Set up LCU in a running desktop to configure a detected Pi, Codex CLI, or Claude Code installation. LCU requires the official ChatGPT Linux app to be installed in the sandbox; it does not install or authenticate agent clients. Silo does not coordinate agent input. Guest applications can access display :1 as silo. Older sandboxes require migration or recreation before account access. Terminals, SSH, editors, and desktop applications share this account; use sudo for administration. An SSH project does not automatically redirect a computer-use plugin into the sandbox.

Logs and activity

Logs searches retained history for the selected sandboxes, including stopped sandboxes. Add source or date filters to narrow the search and remove their chips to reset them. Scroll the list to fetch more matching records. Expand an individual record to read its complete fetched text. Follow refreshes recent output; Pause lets you inspect it. Activity shows sandbox operations and their results.

Silo keeps logs for at most seven days, with separate 125 MiB limits for execution records and runtime/kernel console output per sandbox (250 MiB total). Console output cannot evict execution records. Oldest segments within each budget are removed first; records in a segment can expire up to a day early. The displayed history boundary tells you what is still available. Computer connection errors and expired history are reported separately from log messages.

Copy copies the fetched records with their timestamps and identities. Save logs… saves all matching records, including pages you have not loaded, as a JSON Lines file. You can cancel; an incomplete save does not replace an existing file. Saved files remain yours until you delete them. Review logs for private information before sharing them.

Remote computers

On the owning computer, enable SSH access through the operating system (Remote Login on macOS), then enable Allow remote management in Settings, Computers. On the connecting computer, choose Connect computer… and paste the displayed address. Both computers need compatible Silo versions. Keep Silo running on the owning computer. Its GitHub account, secrets, exports, and imports remain managed there.

An offline computer shows its sandboxes' last known status. Reconnect before changing them. During an update, wait for fresh status before starting another operation.

Menus, navigation, and settings

On Linux, click Menu in the window toolbar, tap Alt, or press F10 to reveal the application menu. Use arrow keys to navigate and Escape to dismiss it. On macOS, use the menu bar at the top of the screen.

Search or Jump To… (⌘K on macOS, Ctrl K on Linux) finds pages, available sandbox actions, and update actions. The Go menu provides direct navigation. Open Silo → Settings… with ⌘, on macOS to configure startup behavior, preferred applications, notifications, appearance, and the pre-upgrade backup under Storage while one exists.

Closing the main window leaves Silo running when a status icon is available; otherwise it quits. Open Silo returns to the main window. Quit stops local sandboxes and preserves their disks. Sandboxes on other computers keep running. When local sandboxes are running, confirm with Quit and stop. A shutdown failure keeps Silo open with an error.

Updates

Silo checks shortly after launch and daily while open; failed checks retry automatically. Turn automatic checks off in Settings if needed. Silo → Check for Updates… opens Updates and checks for a release. You choose when to download and install. Save work before confirming an update that stops running sandboxes. Silo restarts those sandboxes after updating. A failed check does not mean your version is up to date.

Linux AppImage installations support in-app updates. For Debian installations enrolled in Silo's software source, quit Silo and use Software Updater. For a manual installation, choose View installers on GitHub, open the release's Assets, and download the installer for your system.

Help with a problem

Read the operation's error and suggested next step. When Details is available, expand it for diagnostics and use its copy control. Check Logs and Activity for the affected sandbox. Open System issue when Silo reports a system problem; relaunch Silo to rerun startup checks. When reporting a problem, include your Silo version, operating system, and steps to reproduce it. Remove credentials and private information before sharing logs.
