Silo Help

Silo runs Linux development sandboxes on macOS and Linux. A sandbox has its own operating system, files, and resources. Its workspace is the /workspace folder and disk. Sandbox disks remain separate from the Silo application.

Sandboxes and the sandbox page

Use Add above the sandbox list to create a sandbox, connect a computer, or choose Import sandbox…. Choose a sandbox's name to open its page. Drag a sandbox by its handle, or focus the handle and press the arrow keys, to change its place in the list. This computer keeps its own order, for its sandboxes and those on other computers; sandboxes that need attention stay at the top. The page header provides Terminal, Editor, and start or stop controls. Stopping or restarting a running sandbox asks for confirmation.

The sandbox page has an Overview tab for settings, secrets, and ports; Checkpoints for saved checkpoints; Storage for local disk usage; and SSH for supported sandbox connections. Tabs appear only when the sandbox supports them. An SSH host is a computer you connect to over SSH, rather than a sandbox Silo creates and manages.

Use the sandbox's actions menu to edit its settings in place. Duplicate settings copies settings into a new empty sandbox. On computers with built-in computer use, the new sandbox includes a desktop that starts automatically with the sandbox, even if the original used manual desktop startup. Fork… creates a new sandbox with a copy of this one's files, starting from its current state. A fork is stopped until you start it. CPU and memory edits stop a running sandbox and apply on its next start. Existing sandbox names and disk sizes cannot change.

Delete… asks you to confirm permanent deletion and explains which files and checkpoints will be removed. Stop a running sandbox first. Where offered, Export, then delete saves and verifies an export file before deleting the sandbox. Delete permanently deletes it without an export.

Overview: secrets and ports

The sandbox page's Overview tab shows its settings, assigned secrets, and ports. Manage credentials in Secrets and choose which sandboxes and HTTPS domains can use them. GitHub repository access and Git identity are configured in GitHub. Check the operation result; Silo tells you when a change requires a restart.

Network shows ports across sandboxes. A website port opens at an address of its own sandbox, such as http://dev-1a2b3c4d.localhost:43000, so its cookies stay separate from other local services and sandboxes. Safari needs macOS 26 or later to resolve these names automatically; on earlier macOS versions, choose Chrome or Firefox in Settings. Use Copy 127.0.0.1 address if your browser cannot resolve the sandbox's address or your development server rejects other host names. The 127.0.0.1 address shares its cookie host with other local services and sandboxes. A sandbox website can still send requests to other services on this computer, so open it only when you trust its code.

Checkpoints, Fork, and Restore

Open the sandbox page's Checkpoints tab. New checkpoint captures its current session and disks. Restore rewinds the same sandbox to a checkpoint after saving a recovery checkpoint. It leaves the sandbox stopped. Restore does not undo changes outside the sandbox, such as pushed commits or sent requests.

Use a checkpoint's actions menu to choose Fork… and create a new stopped sandbox with a copy of its files, or Export… to save a local checkpoint to an export file. Checkpoint history remains on the computer that owns the sandbox.

Delete checkpoint data in Silo on the sandbox's owning computer: choose Delete… in the checkpoint's actions menu when available, then confirm. When viewing a sandbox on a connected computer, open Silo on that computer to delete its checkpoints. Delete can be unavailable if this is the latest state the sandbox builds on, or if later checkpoints, exports, or another sandbox still need it. Read the reason shown beside the checkpoint. Deleting a sandbox removes checkpoint data that nothing else needs; retained data is released when its remaining dependencies are removed, which can include deleting a dependent checkpoint. The Storage tab shows checkpoint disk usage.

Export and Import

Choose Export… from a local sandbox's actions menu and pick a folder to save a .silo-backup export file containing its disks. A running sandbox keeps running. Checkpoint history is not included. Import creates a new stopped sandbox from the exported disks, without the captured memory session.

Choose Add then Import sandbox… above the sandbox list, or File → Import Sandbox… in the application menu. Select an export file; Silo verifies it and asks for a sandbox name. Import does not replace an existing sandbox. Keep export files off the owning computer for another copy, or import one on another compatible computer to move your work.

Storage and files

Open a local sandbox's Storage tab to compare workspace space allocated on this computer with space used inside the sandbox. Workspace storage holds /workspace; runtime storage holds the operating system and installed tools. Deleted workspace files can leave unused space allocated in the disk image. Start the sandbox and use Reclaim unused space to release it without deleting files. Reclamation releases unused allocated space on this computer; workspace capacity and files stay the same. It does not reclaim runtime storage or checkpoints. If Silo asks for a restart, restart before reclaiming.

Silo also reclaims automatically after seven days since the last success, and before a normal stop when the last success was at least 24 hours ago. A sandbox without a previous successful reclaim is eligible on its next start. Failed automatic attempts wait at least 24 hours before retrying. Quit gives reclamation a shared 15-second command budget across local sandboxes; a failed reclaim does not prevent normal shutdown.

After an upgrade that converts your sandboxes to new storage, Silo keeps the previous storage as a pre-upgrade backup in case something looks wrong. The migration screen shows its size and the date Silo deletes it automatically, 14 days after the upgrade. Open Settings → General → Storage to see it again: Show reveals the folder in your file manager, and Delete now deletes it permanently after you confirm. The folder holds Linux disk images, so you can copy it elsewhere but not browse files in it. Downgrading to an earlier Silo is not supported. The backup is deleted only after every sandbox was converted; if you chose to continue after a failed migration, Silo keeps the original sandbox data and never deletes it.

Files browses sandbox directories. Start the sandbox before browsing its files.

SSH access

Open the sandbox page's SSH tab, from its ⋯ menu or by clicking its SSH badge, to review connections and authorized keys. SSH from the owning computer and SSH from other computers are separate settings. Allow SSH from other computers exposes the selected address and port to that network and asks for confirmation. Only authorized keys can sign in. Use Copy terminal command or Save key file in the connection's actions menu. A downloaded key file is private; keep it secure.

Linux desktop and computer use

New sandboxes on a computer with built-in computer use include a Linux desktop for agents (Claude Code, Codex, Pi, OMP and Hermes). Nothing needs to be added: the desktop starts with the sandbox, and Open Linux desktop opens its viewer. These sandboxes' Edit form does not offer Add Linux desktop or Start desktop with sandbox. If a connected computer runs an older Silo, the creation form offers the optional desktop instead; update Silo on that computer for built-in computer use.

ChatGPT for Linux. Silo downloads ChatGPT for Linux from OpenAI so agents in your sandboxes can use the Linux desktop. It happens by itself, in the background, on every computer that runs Silo: nothing to accept, and creating or starting a sandbox never waits for it. The download is about 450 MB (about 1.5 GB on disk) once per computer, shared read-only by that computer's sandboxes; Silo does not install it inside them. If it cannot reach OpenAI (offline, or a firewall holding Silo's connection) it tries again later by itself. Settings → Computers shows nothing about it while it works. If the download fails, or Silo cannot read its state on a connected computer, a Computer use components section names that computer and the reason and offers Retry or Refresh. A computer running an older Silo is not reported.

Computer use section. The sandbox's Overview page shows its state (preparing, installing, ready, failed, or unavailable) with the reason. Download failed means its computer could not prepare the ChatGPT app; use Retry in the download panel. Agent setup becomes available after that download finishes. Details lists the app, runtime and LCU versions and the agents that were configured. If the combination of versions has not been tested with Silo, a warning appears; computer use still works but may misbehave.

Allow without asking is off by default, and Settings → Computers has a switch, Allow agents to use the computer without asking in new sandboxes, that sets what sandboxes you create or import start with (also off by default; sandboxes on a connected computer included). Duplicates keep their source's choice, and an imported archive never carries one. Claude Code and Codex then ask before using the computer, as they do for other tools. Pi and Hermes have no such approval and OMP does not prompt by default, so the switch changes nothing for them unless you set OMP to ask. Turn it on and the agents that ask stop asking in this sandbox. It affects only this sandbox and its computer-use actions; it does not limit what an agent can do in accounts you are signed in to inside the sandbox, such as in a browser. Silo applies a change in the background and shows Applying… until it is done; if it fails or only some agents change, the panel says so and warns that some agents may still act without asking, and Silo tries again when the sandbox starts. The switch configures the agents' approval prompts and is not a security boundary inside the sandbox. If Silo cannot read the setting, it says so and disables the switch until it can. Other tools keep their own approvals.

Set up computer use (on the Overview page and in the desktop viewer) reconfigures agents while the sandbox and its Linux desktop are running. Start the desktop from its viewer first if it is stopped. Use setup after installing a new agent. Reconnect agent sessions afterward so they load computer use.

Linux desktop in older sandboxes

Sandboxes created before computer use was built in keep the optional desktop described here. The built-in, automatic computer use above needs a new sandbox; older sandboxes keep the manual Set up LCU path below, which installs the legacy LCU 0.4.0.

Select Linux desktop when creating a sandbox, or choose Add Linux desktop from an existing sandbox's actions menu. Installation adds Xfce to the same Ubuntu sandbox; files and terminal tools stay in place. Desktop packages remain installed.

Start desktop with sandbox is on by default. Turn it off to start the desktop explicitly from its viewer. Turning it off leaves an existing session running. Stopping the sandbox always stops its desktop. An explicit desktop stop lasts until you start it again or the sandbox next starts with automatic startup enabled. If the viewer offers Update desktop instead of Start desktop, keep the sandbox running and the desktop stopped, choose Update desktop, then Start desktop. Updating the desktop does not start it automatically.

Open Linux desktop opens the interactive viewer. Closing the viewer leaves applications running. Stopping or restarting the desktop closes graphical applications, so save your work first. Independent terminal jobs continue. Install additional Linux applications from the desktop terminal; the silo account has passwordless sudo.

Adding a Linux desktop does not install agent tools. LCU is the supported computer-use integration: choose Set up LCU in a running desktop to configure a detected Pi, Codex CLI, or Claude Code installation. LCU requires the official ChatGPT Linux app to be installed in the sandbox; it does not install or authenticate agent clients. Silo does not coordinate agent input. Guest applications can access display :1 as silo. Older sandboxes require migration or recreation before account access. Terminals, SSH, editors, and desktop applications share this account; use sudo for administration. An SSH project does not automatically redirect a computer-use plugin into the sandbox.

Logs and activity

Logs searches retained history for the selected sandboxes, including stopped sandboxes. Add source or date filters to narrow the search and remove their chips to reset them. Scroll the list to fetch more matching records. Expand an individual record to read its complete fetched text. Follow refreshes recent output; Pause lets you inspect it. Activity shows sandbox operations and their results.

Silo keeps logs for at most seven days, with separate 125 MiB limits for execution records and runtime/kernel console output per sandbox (250 MiB total). Console output cannot evict execution records. Oldest segments within each budget are removed first; records in a segment can expire up to a day early. The displayed history boundary tells you what is still available. Computer connection errors and expired history are reported separately from log messages.

Copy copies the fetched records with their timestamps and identities. Save logs… saves all matching records, including pages you have not loaded, as a JSON Lines file. You can cancel; an incomplete save does not replace an existing file. Saved files remain yours until you delete them. Review logs for private information before sharing them.

Remote computers

On the owning computer, enable SSH access through the operating system (Remote Login on macOS), then enable Allow remote management in Settings, Computers. On the connecting computer, choose Connect computer… and paste the displayed address. Both computers need compatible Silo versions. Keep Silo running on the owning computer. Its GitHub account, secrets, exports, and imports remain managed there.

An offline computer shows its sandboxes' last known status. Reconnect before changing them. During an update, wait for fresh status before starting another operation.

Menus, navigation, and settings

On Linux, click Menu in the window toolbar, tap Alt, or press F10 to reveal the application menu. Use arrow keys to navigate and Escape to dismiss it. On macOS, use the menu bar at the top of the screen.

Search or Jump To… (⌘K on macOS, Ctrl K on Linux) finds pages, available sandbox actions, and update actions. The Go menu provides direct navigation. On macOS, open Silo → Settings… (Silo Dev → Settings… in Silo Dev), or press ⌘,, to configure startup behavior, preferred applications, notifications, appearance, and the pre-upgrade backup under Storage while one exists.

Closing the main window leaves Silo running when a status icon is available; otherwise it quits. Open Silo returns to the main window. Quit stops local sandboxes and preserves their disks. Sandboxes on other computers keep running. When local sandboxes are running, confirm with Quit and stop. A shutdown failure keeps Silo open with an error.

Updates

These update instructions apply to the production Silo app. Silo Dev has no update feed and does not install production releases. With automatic checks enabled, Silo checks shortly after launch, when you return to Silo, and daily while open; failed checks retry automatically. Turn automatic checks off in Settings if needed. Silo → Check for Updates… opens Updates and checks for a release. You choose when to download and install. Save work before confirming an update that stops running sandboxes. Silo restarts those sandboxes after updating. A failed check does not mean your version is up to date.

Linux AppImage installations support in-app updates. Debian installations enrolled in Silo's software source offer Update inside Silo. Your system asks for administrator authentication; Silo refreshes package information, installs the update, and restarts. If you use Software Updater or install a package outside Silo, quit Silo first. For a manual installation, choose View installers on GitHub, open the release's Assets, and download the installer for your system.

Help with a problem

Read the operation's error and suggested next step. When Details is available, expand it for diagnostics. Use the copy control when one is offered. Check Logs and Activity for the affected sandbox. Open System issue when Silo reports a system problem. Follow its recovery instructions and choose Retry checks to run the checks again. When reporting a problem, include your Silo version, operating system, and steps to reproduce it. Remove credentials and private information before sharing logs.
